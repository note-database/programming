
این Round خیلی مهم است، چون در Round بعدی که وارد UI/UX می‌شویم باید بدانیم **برای چه ذهنیتی طراحی می‌کنیم**. باز هم کنار هر سؤال پیشنهاد خودم را می‌گذارم.

1. **اگر قرار باشد دو Persona برای Demoهای محصول انتخاب کنیم، چه کسانی باشند؟** توجه کن این به معنی محدود کردن خود Template نیست؛ فقط محتوای Demo باید یک شخصیت واقعی داشته باشد. گزینه‌های خوب: `Developer + UI/UX Designer`، `Developer + Creative Freelancer`، `Designer + Photographer` یا دو شخصیت کاملاً عمومی. پیشنهاد من: **Demo 01 = Front-end / Creative Developer** و **Demo 02 = UI/UX / Digital Designer**. این دو هم بازار خوبی دارند و هم اجازه می‌دهند قابلیت‌های قالب را از دو زاویه متفاوت نشان دهیم.
    
2. **خریدار در اصل چرا این قالب را می‌خرد؟** برای پیدا کردن شغل، گرفتن پروژه فریلنس، Personal Branding، معرفی کسب‌وکار شخصی، رزومه آنلاین یا ترکیبی؟ پیشنهاد من: محصول را حول یک نیاز بزرگ‌تر تعریف کنیم: **«ساخت سریع یک حضور حرفه‌ای آنلاین که هم شخص را معرفی کند و هم کیفیت کارهایش را ثابت کند.»** در نتیجه هم Job Seeker، هم Freelancer و هم Creative Professional داخل بازار هدف قرار می‌گیرند.
    
3. **سه مشکل اصلی که می‌خواهی محصولت در قالب‌های موجود حل کند چیست؟** چند گزینه: طراحی قدیمی، Portfolio ضعیف، Customization سخت، کد شلوغ، Responsive ضعیف، Documentation بد، نسخه RTL/LTR ضعیف، Dark Mode ناقص، وابستگی زیاد، ظاهر Generic. پیشنهاد شخصی من برای Top 3: **Generic/dated design + weak project presentation + difficult customization/documentation**.
    
4. **خریدار پس از باز کردن فایل ZIP باید چقدر سریع بتواند سایت را شخصی کند؟** پیشنهاد من این است که یک کاربر با دانش مقدماتی HTML باید بتواند طی حدود یک نشست کوتاه، بدون فهم architecture، حداقل **نام، عکس، Bio، لینک‌ها، رنگ Accent، Resume و چند Project** را عوض کند. برای رسیدن به این هدف باید کد و Documentation را عمداً طراحی کنیم، نه اینکه در آخر README بنویسیم.
    
5. **آیا می‌خواهی خریدار برای استفاده از نسخه نهایی به Node/npm یا Build Command احتیاج داشته باشد؟** انتخاب‌ها عملاً دو فلسفه‌اند: `Developer-oriented source with build process` یا `Download → Edit → Open index.html`. پیشنهاد من برای محصول Marketplace: **هیچ Build Step اجباری برای مصرف‌کننده نداشته باشیم.** حتی اگر در Development از tooling استفاده کردیم، خروجی نهایی باید قابل استفاده مستقیم باشد.
    
6. **مستندات را فارسی، انگلیسی یا دو زبانه می‌خواهی؟** پیشنهاد من: **مستندات اصلی انگلیسی ساده و دقیق + راهنمای فارسی برای خریداران راست‌چین**. اگر فقط فارسی بنویسیم LTR/English package ضعیف‌تر به نظر می‌رسد؛ اگر فقط انگلیسی باشد برای بخشی از مشتریان ایرانی friction ایجاد می‌کند.
    
7. **محتوای Demo چقدر واقعی باشد؟** آیا Lorem Ipsum و نام‌های کلی قبول است یا دو شخصیت کامل بسازیم؟ پیشنهاد من شدیداً **Realistic Demo Content** است. یعنی برای هر Persona نام، عنوان شغلی، Bio، Skills، Experience، Projectها، Case Studyها و Blog Postهایی بنویسیم که مثل سایت واقعی دیده شوند. Marketplace Screenshot با محتوای مصنوعی خیلی سریع ارزان به نظر می‌رسد.
    
8. **خریدار هنگام دیدن صفحه فروش چه چیزی باید باعث اعتمادش شود؟** گزینه‌ها شامل Demo قوی، Clean Code، Documentation، Update Policy، Responsive، RTL/LTR، SEO، Performance، Support و Changelog هستند. پیشنهاد من این است که اعتماد را با سه مدرک بسازیم: **Live Demo حرفه‌ای + مستندات واضح + Quality Metrics واقعی**؛ نه فقط عبارت‌هایی مثل «کدنویسی فوق حرفه‌ای».
    
9. **می‌خواهی محصول برای شخصی‌سازی یک سیستم مشخص داشته باشد؟** مثلاً تمام Color/Spacing/Radius/Typography tokenهای اصلی در یک محل تعریف شوند تا مشتری مجبور نباشد بین 20 فایل بگردد. پیشنهاد من: **حتماً بله.** بعدها در Design System مشخص می‌کنیم با CSS Custom Properties، فایل config یا ساختاری ترکیبی انجام شود.
    
10. **آیا مشتری باید بتواند Sectionها را راحت حذف، جابه‌جا یا Duplicate کند؟** پیشنهاد من: **بله، تا حد منطقی.** هر Section باید تا جای ممکن مستقل باشد، ولی نباید به سمت Page Builder مصنوعی برویم. مثلاً حذف `Clients` نباید باعث Error در JavaScript یا شکستن Navigation شود.
    
11. **چقدر برای مشتری Non-technical اهمیت قائل شویم؟** سه سطح داریم: فقط Developer، کاربر آشنا با HTML، یا تقریباً بدون دانش کدنویسی. پیشنهاد من: **کاربر آشنا با HTML را کف هدف قرار بدهیم، نه فرد کاملاً بدون دانش کدنویسی.** چون اگر بخواهیم HTML Template را برای فرد کاملاً غیرتکنیکال طراحی کنیم، کم‌کم مجبور می‌شویم CMS یا Builder بسازیم که خارج از Scope است.
    
12. **در نسخه اول، «احساس» خریدار بعد از دیدن Demo باید چه باشد؟ فقط سه صفت انتخاب کن.** نمونه‌ها: Premium، Modern، Creative، Clean، Technical، Elegant، Bold، Trustworthy، Sophisticated، Minimal، Energetic. پیشنهاد من برای جهت فعلی پروژه: **Modern + Sophisticated + Creative**. `Minimal` باید ویژگی طراحی باشد، نه احساسی که محصول را خالی و ساده نشان دهد.
    
13. **آیا می‌خواهی ظاهر Persian RTL دقیقاً هم‌سطح LTR باشد یا LTR نسخه اصلی و RTL صرفاً Adaptation آن؟** پیشنهاد من: **هیچ‌کدام نسخه درجه‌دو نباشند.** Design System باید Bi-directional باشد و در RTL فقط همه چیز Mirror نشود؛ بعضی compositionها ممکن است نیاز به تصمیم طراحی مستقل داشته باشند.
    
14. **آیا می‌خواهی در صفحه محصول روی تعداد Feature مانور بدهیم یا روی کیفیت Experience؟** پیشنهاد من: **Experience-first marketing**. بعد Featureها را به‌عنوان Evidence ارائه کنیم. مثلاً به‌جای «دارای 27 قابلیت»، بگوییم Case Study حرفه‌ای، Customization متمرکز، RTL/LTR واقعی، Dark/Light، Responsive و Documentation دقیق.
    
15. **Update Strategy محصول چه باشد؟** فقط Bug Fix، یا بعد از انتشار Featureهای از پیش برنامه‌ریزی‌شده هم داشته باشیم؟ با توجه به جواب‌های قبلی تو، پیشنهاد من: **v1 محدود و polished**؛ سپس مثلاً Testimonials، Services، Pricing، PHP Contact و Variationهای بیشتر فقط براساس Feedback و ارزش واقعی وارد `v1.x` شوند. از الان نباید قول دهیم همه‌شان حتماً اضافه می‌شوند.
    
16. **می‌خواهی مشتری احساس کند یک Template آماده خریده یا یک Starter Kit قابل توسعه؟** پیشنهاد من ترکیب این دو است ولی با اولویت Template: **Ready-to-use portfolio template with developer-friendly structure.** محصول باید در لحظه زیبا و کامل باشد، ولی Developer هم وقتی کد را باز می‌کند احساس نکند با فایل‌های درهم‌ریخته طرف است.
    
17. **چه چیزی را حاضر نیستی برای بیشتر شدن فروش قربانی کنی؟** مثلاً Performance، Code Quality، Accessibility، ظاهر، تعداد Demo، زمان انتشار یا Simplicity. پیشنهاد من این است که سه خط قرمز داشته باشیم: **Code Quality + UX Quality + Maintainability**. تعداد Features و Demoها اولین چیزهایی هستند که در صورت فشار زمانی حذف می‌شوند.
    
18. **از نظر خودت موفقیت نسخه اول را با چه چیزی می‌سنجیم؟** فقط تعداد فروش کافی نیست. می‌توانیم فروش، نرخ رضایت، تعداد Support Ticket، نرخ Refund، نظر خریداران، Bugs گزارش‌شده، تأیید سریع راست‌چین و کیفیت برند را بسنجیم. پیشنهاد من برای محصول اول: **تأیید بدون مشکلات جدی + بازخورد کیفی خوب + Bugs کم + اولین فروش‌های ارگانیک** مهم‌تر از یک عدد فروش بزرگ در هفته اول است.
    

برای جواب دادن مثل قبل فقط شماره را بنویس. مخصوصاً روی **3، 7، 12 و 17** کمی فکر کن؛ این چهار جواب مستقیماً Art Direction و معماری محصول را تغییر خواهند داد.

بعد از Round 2، می‌رویم سراغ **Round 3 — Information Architecture, Pages & Feature Scope** و آنجا دقیقاً تعیین می‌کنیم چه Sectionها و صفحه‌هایی در v1 وجود دارند و چه چیزهایی رسماً وارد Backlog آپدیت‌ها می‌شوند.
