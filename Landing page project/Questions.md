کاملاً منظورت را فهمیدم. این پروژه را مثل یک **محصول تجاری واقعی** می‌بینیم، نه یک تمرین فرانت‌اند.

یک نکته مهم هم از بررسی فعلی راست‌چین: دسته‌ی مستقلی برای «قالب لندینگ HTML» وجود دارد و در همین صفحه محصولاتی با حدود **۶۹۵ تا ۹۹۸ هزار تومان** دیده می‌شوند؛ تعداد فروش هم از صفر تا بیش از ۱۵۰ متغیر است. مثلاً بعضی محصولات جدید چندمنظوره فعلاً صفر فروش دارند، در حالی که یک لندینگ معرفی اپلیکیشن ۱۵۵ فروش ثبت کرده است. این به‌تنهایی اثبات نمی‌کند که «نیچ بهتر از چندمنظوره است»، اما علامت خوبی است که صرفاً ساختن یک لندینگ شیک و عمومی مزیت رقابتی کافی نیست. [راست چین](https://www.rtl-theme.com/category/template-html/html-landing-page/)

خود راست‌چین هم در صفحه فروشندگان روی **تحلیل بازار، نیازسنجی، بهبود فنی محصول و پرزنت حرفه‌ای** تأکید دارد. بنابراین ما دقیقاً همین مسیر را قبل از کدنویسی انجام می‌دهیم. [راست چین](https://www.rtl-theme.com/become-vendor/)

می‌خواهم جواب سؤالات زیر را بدهی. لازم نیست جواب‌ها طولانی باشند؛ حتی `1) ... 2) ...` کافی است. اگر جواب چیزی را نمی‌دانی، دقیقاً بنویس **«نمی‌دانم، تو پیشنهاد بده»**. آن موارد را من تصمیم‌گیری و به چالش می‌کشم.

220. آیا در پایان هر Phase summary از تغییرات + مشکلات + technical debt بدهد؟

### بخش W — فازبندی

پیشنهاد اولیه من این است که پروژه را تقریباً این‌گونه جلو ببریم:

`Research → Product Definition → UX/IA → Design System → Skeleton → Sections → Interactions → Responsive → Accessibility → Performance → SEO → Documentation → QA → Marketplace Release`

اما قبل از قطعی کردن:

221. دوست داری هر فاز کوچک و کنترل‌شده باشد یا چند فاز بزرگ؟
222. آیا در پایان هر فاز شخصاً کد را بررسی می‌کنی؟
223. آیا می‌خواهی من هم بعد از هر Phase خروجی Codex را با تو review کنم؟
224. آیا Codex نباید کل سایت را یک‌باره تولید کند؟ پیشنهاد من: **قطعاً نباید.**
225. ترجیح می‌دهی ابتدا فقط Hero را production-quality کنیم و بعد Design Language را روی بقیه تعمیم دهیم؟
226. قبل از کدنویسی، wireframe متنی کل صفحه را بسازیم؟
227. قبل از wireframe، section strategy و conversion flow را مشخص کنیم؟
228. آیا Design Tokens قبل از هر UI code نهایی شوند؟
229. آیا responsive و accessibility همزمان با هر section انجام شوند یا در فاز جدا؟ پیشنهاد من: پایه‌شان همزمان، audit نهایی جدا.

### بخش X — Scope Control

230. حداکثر زمانی که می‌خواهی روی نسخه 1.0 بگذاری چقدر است؟
231. ترجیح می‌دهی مثلاً ۳ هفته محصول قوی داشته باشیم یا ۶ هفته محصول کامل‌تر؟
232. روزانه تقریباً چند ساعت برای این پروژه می‌گذاری؟
233. آیا تاریخ انتشار مشخصی داری؟
234. اگر feature خوبی scope را زیاد کند، حذفش کنیم یا زمان انتشار را عقب بیندازیم؟
235. MVP برایت قابل قبول است یا اولین نسخه باید Feature-rich باشد؟
236. آیا می‌توانیم بعضی قابلیت‌ها را برای v1.1 نگه داریم؟

### بخش Y — بسته نهایی برای راست‌چین

237. می‌خواهی فایل نهایی خریدار کاملاً جدا از development source باشد؟
238. ساختار مثلاً `Documentation / Main Files / Sources` مناسب است؟
239. Demo URL آنلاین خواهیم داشت؟
240. GitHub Pages برای Demo کافی است یا دامنه مستقل؟
241. می‌خواهی برای محصول screenshot و preview assets هم بعداً طراحی کنیم؟
242. آیا نام تجاری محصول هم باهم انتخاب کنیم؟
243. توضیحات صفحه محصول راست‌چین را هم در انتها باهم بنویسیم؟
244. لیست ویژگی‌های فروش محصول را هم آماده کنیم؟
245. changelog اولیه؟
246. FAQ مخصوص خریداران؟
247. متن پشتیبانی و قوانین Support؟
248. roadmap نسخه‌های آینده؟

### بخش Z — تصمیم‌های شخصی تو

249. مهم‌ترین چیز برای خودت در این پروژه چیست؟
250. از چه چیزی بیشتر می‌ترسی: طراحی ضعیف، کد ضعیف، عدم فروش، طولانی شدن پروژه یا رد شدن محصول؟
251. فکر می‌کنی نقطه قوت اصلی خودت در این پروژه چیست؟
252. کدام قسمت را می‌خواهی خودت بیشتر بنویسی و Codex فقط کمک کند؟
253. کدام قسمت را می‌خواهی Codex بیشتر برعهده بگیرد؟
254. آیا هدف آموزشی داری که مجبورمان کند بعضی قسمت‌ها را عمداً خودت پیاده‌سازی کنی؟
255. می‌خواهی وقتی Codex کد تولید کرد، من فقط آن را اصلاح کنم یا **مجبورت کنم دلیل کد را هم بفهمی**؟
256. اگر بین «سریع تمام کردن» و «محصول بهتر» مجبور به انتخاب شویم، انتخابت چیست؟

---

و سه تصمیم را من از همین الان پیشنهاد می‌کنم مگر اینکه مخالفت کنی:

**اول:** فعلاً هیچ ایده‌ای مثل «SaaS Landing Page» را قطعی نمی‌کنیم. این هنوز ایده نیست؛ فقط یک category است. باید به چیزی مثل «Landing page for X solving Y for Z customer» برسیم.

**دوم:** Codex نباید یک‌باره کل پروژه را generate کند. این تقریباً تضمین می‌کند معماری، consistency و جزئیات UI افت کنند. Master Prompt ما در نهایت Codex را مجبور می‌کند با **Phase Gates** کار کند: `Plan → Implement → Test → Review → Stop`.

**سوم:** در Master Prompt فقط درباره ظاهر حرف نمی‌زنیم. Context نهایی شامل **Product Strategy + Target Buyer + Design Direction + Tech Constraints + Architecture + Code Standards + Accessibility + Performance + SEO + Documentation + QA + Marketplace Packaging + Codex Operating Rules + Phase-by-Phase Execution Protocol** خواهد بود.

بعد از جواب تو، من جواب‌هایت را تحلیل می‌کنم، تناقض‌ها و تصمیم‌های ضعیف را به چالش می‌کشم و اگر لازم باشد **Round 2 سؤال‌های دقیق‌تر** را فقط روی نقاط مبهم می‌پرسم. بعد از تثبیت Specification، همان **Master Context Prompt انگلیسی برای Codex** را می‌سازیم.
